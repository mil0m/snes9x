**Status (2026-10-31):** ideas, sorted into scopes with Mikael. Nothing here is planned in
detail yet; each item gets its own plan section before it is built. ROM corruption (#22,
[the ROM plan](./2026-10-31-rom-corruption-plan.md)) finishes first.

## The idea

Most code corruption crashes because the CPU ends up somewhere that isn't an instruction:
a stream read out of step, a jump into data, a broken stack. But SNES games are built
around a few patterns that let us make changes that are **wrong but valid**: the game
does the wrong thing with its own working parts, so it keeps running.

- **Dispatchers.** State machines (game mode, each enemy's AI state, each menu screen)
  run through jump tables: `JMP (table,X)`, `JSR (table,X)`, `JML [ptr]`, or a pushed
  address and `RTS`. Swapping one entry for another entry of the same table always lands
  on a real routine.
- **State variables.** The index into a dispatcher usually comes from a WRAM byte. Setting
  it to another value it has held teleports the game to another valid state.
- **Script engines.** RPGs run event scripts, battle AI and text as bytecode: read a byte
  from ROM, jump through a table indexed by it. Corrupting the script in its own
  vocabulary is opcode swap one level up.
- **Functions.** Every `JSR`/`JSL` target is an entry. An `RTS`/`RTL` there skips the
  whole routine with the stack balanced.
- **Tables.** `LDA table,X` with the X values seen gives a table's base, size and record
  stride, so records and columns can be corrupted as units.

The tracer from #22 phase 3 already sees every instruction run from ROM. These items
make it record a little more, then build operations on what it learned.

The motivating golden moment (Mikael): starting A Link to the Past, the three Triforce
pieces flew past each other and away instead of meeting and turning in the middle. That
is a wrong-but-valid change: the motion ran, with a wrong target, speed or stop check.
Producing moments like that on purpose, and keeping them, is the goal.

**A key finding:** with an LLM, mapping a game's structure per game becomes practical.
The tracer collects facts (tables, call graph, what's read when a battle starts); Claude
reads them with the disassembly and names things ("the battle command dispatcher, 29
entries"). Work far too slow by hand becomes a profile per game, which unlocks
game-specific corruption.

## Scope 1: the tracer learns the game's structure (#25-#31)

All of these extend the phase 3 tracer and are measured against its 4-7% cost. They
learn while you play, are saved per person in the library and combined, like the code map.

| # | Item | What it records |
|---|---|---|
| 25 | Jump tables and dispatchers | Indirect jumps and calls from ROM: the table's address, the entries used, the index register's value, and where that index was loaded from |
| 26 | The call graph | Function entries, by call type (`JSR` near, `JSL` long), who calls them, how often per frame |
| 27 | Table shapes | Indexed reads from ROM: base, index range, record stride; tables that are read together |
| 28 | State variables and index ranges | WRAM bytes that feed dispatchers and table indexes, and every value each has held |
| 29 | Where RAM came from | ROM bytes copied into WRAM (by loops or DMA): this WRAM area is a copy of that ROM table |
| 30 | Code in WRAM | The tracer on code run from WRAM (FF6's title screen runs at `$7E:7195`) |
| 31 | What code tells the hardware | `LDA #imm` linked to the `STA $21xx` it feeds: which operand sets the BG mode, mosaic, colour math, windows, mode 7 |

## Scope 2: wrong-but-valid operations (#32-#40)

New ops for recipes, built on scope 1. Each states what it needs.

| # | Op | Does | Needs |
|---|---|---|---|
| 32 | Pointer swap | Replace a jump-table entry with another entry of the same table. Mikael's favourite | #25 |
| 33 | State jump | Set a state variable to another value it has held | #25, #28 |
| 34 | Kill switches | Toggle a function off live (`RTS`/`RTL` at its entry), on hotkeys, ranked by how often it runs | #26 |
| 35 | Function redirection | Point a call at another function of the same call type | #26 |
| 36 | Record ops | Swap two records, shuffle one column across all records, nudge one field everywhere | #27 |
| 37 | Bounded RAM corruption | Corrupt an index only within (or just past) the values it has held: a safety option for RAM rules | #28 |
| 38 | Random tables | Flatten or skew a game's random-number table for deterministic weirdness | #27 or a game profile |
| 39 | Hardware operands | Corrupt only operands that configure the PPU, by register | #31 |
| 40 | Corrupt code in WRAM | Code changes the game undoes itself whenever it copies the routine again | #29, #30 |

## Parked and dropped

- **Parked:** corrupting the sound CPU's program and song data (uploaded from ROM through
  `$2140-$2143`). Not a priority.
- **Dropped:** aiming at branches that have only ever gone one way, to open code that
  never ran.

## Answered questions (2026-10-31)

- *Does a state jump (#33) need the game to run for a while first?* Yes: it can only jump
  to values it has seen. But learning is passive (it records whenever a game is loaded,
  like the code map), it's combined across people (Erik's play teaches Mikael's copy),
  and a game profile (#41) can name states nobody has reached yet.
